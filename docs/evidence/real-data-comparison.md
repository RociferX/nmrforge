## 0. Why the data was replaced, and how it was chosen

**The immediate reason**: the previous data set was the HSQC of a **viral protein**. Viral wording is a
sensitive item in public release, content review and automated classification, and this project needs an
evidence data set that can be cited publicly long-term without importing unrelated controversy. This page
therefore switches the data source entirely to **non-viral, non-pathogenic** material.

**Four hard selection constraints** (failing any one disqualifies a candidate):

1. **Biosafety-neutral** - only bacteria, human, plant, fungal, or **synthetic/standard samples**. Viruses,
   pathogenic bacteria and toxins are excluded (for example the Tc toxin family of *Photorhabdus
   luminescens*, and diphtheria/botulinum/ricin toxins are not eligible).
2. **Must be genuine Bruker time-domain data** - the directory must contain `acqus`/`acqu2s`
   (`/acqu3s`) + `ser`. This constraint eliminated many otherwise suitable legacy NESG entries:
   **most of them are Varian format** (`procpar`/`fid`, no `acqus`/`ser`) and cannot feed the Bruker
   reader. BPTI (5307), the Z domain (5656) and *E. coli* YacG (5335) are all in that class - small
   and harmless, but the **format is wrong**.
3. **The grid must be small** - see the memory convention below. The larger the 3D indirect grid, the
   more extreme SMILE's reconstruction memory becomes, and the real machine cannot run it.
4. **A comparable reference must exist** - either the data ships `pdata/` (a spectrum the data provider
   processed), or it is NUS with an official reconstruction result. Only then does section 1's
   "automatic processing vs reference" have something to compare against.

### Why the grid must be small: SMILE's memory convention

The product's own guard (`backend/memory_guard.py`) estimates peak memory with a model calibrated
against SMILE's startup banner:

```text
peak ~= direct_points x iteration_FT_size(x) x iteration_FT_size(y) x 16 B x 1.06
iteration_FT_size = next_pow2(3 x NusTD), floor 256
```

Under this formula the peak memory of 3D NUS steps with the indirect grid:

| Indirect grid (per dimension) | Iteration FT | Peak (168 direct points) | Safe? |
| --- | --- | --- | --- |
| <= 85 | 256 x 256 | ~0.17 GB | safe zone |
| 86 - 170 | 512 x 512 | ~0.70 GB | safe |
| 171 - 292 | 1024 x 1024 | ~2.78 GB | at the documented **2.8 GB** ceiling |
| larger | larger | > 2.8 GB | over the guard |

> How this was checked: the table is not hand-computed. It was produced by running
> `backend/memory_guard.py::smile_iteration_ft_size` itself point by point (85 -> 256, 86 -> 512,
> 170 -> 512, 171 -> 1024), with the peak evaluated using the same module's `MB_PER_FT_PLANE`
> (16 B/point) and `FT_OVERHEAD` (1.06); 292 -> 1024x1024 -> 2.78 GB agrees with the sampleK
> startup-banner measurement recorded in that module. If the guard constants change, this table must
> be recomputed.

**So "small grid" has a definite meaning in this project: keep every 3D indirect dimension at 85 or
below** - then the iteration FT lands in the smallest 256x256 tier, the peak is under 0.2 GB, and the
run takes seconds to minutes on the real machine rather than crushing it.

> **Only 3D uses this formula.** For the 2D path `estimate_smile_peak_mb` returns `MB_FLOOR_2D = 128 MB`
> directly, independent of the grid - so 2D NUS is light even with a large NusTD. Do not apply the table
> above to 2D.

**Choice #4 had to be changed.** SMILE's official example 4 has `TD=3200` on the 13C indirect dimension,
giving an iteration FT of 16384; the bundle's own `smile.log` states **`Memory used by SMILE: 9.3 GB`**
(on the authors' machine, 4 threads, 9 iterations, 1.2 minutes). Under this project's guard formula it is
**44 GB**, far beyond the documented 2.8 GB ceiling. That **directly conflicts** with the requirement to
keep grids small and avoid excessive load, so it was replaced.

**The replacement and its trade-off**: surveying the headers of every other SMILE 3D example shows that
**none** satisfies "<= 85 per dimension"; the smallest, `ubiq_noesyhsqc_15N` (15N TD=80, 1H TD=620), still
needs ~1.39 GB.

| SMILE 3D example | Indirect grid | FT | Peak |
| --- | --- | --- | --- |
| `ubiq_noesyhsqc_15N` | 80 / 620 | 256 x 2048 | ~1.39 GB |
| `ABeta_noesyhsqc_15N` | 64 / 900 | 256 x 4096 | ~2.78 GB |
| `hncoconh` | 310 / 310 | 1024 x 1024 | ~2.78 GB |
| `hnco` (original choice) | 3200 / 171 | 16384 x 1024 | ~44 GB |
| `noesyhsqc_13C` | 48048 / 1 | 262144 x 256 | ~178 GB |

**Conclusion and how it was handled**: among **genuinely acquired public 3D NUS** data there is no Bruker
data set that satisfies "<= 85 per dimension" - the whole point of 3D NUS is to drop indirect points, and
the official examples deliberately use larger full grids to demonstrate reconstruction quality. So #4 has
three options, and this page takes the third:

1. use SMILE's official `hnco` - **rejected**, 44 GB, directly violates the constraint;
2. use the project's own `tests/fixtures/bruker/nus_3d` (NusTD 48/128) -> ~0.41 GB - workable and the
   smallest, but it is a **synthetic fixture** with no real `ser`, so its evidential value is weak;
3. **downsample the BMRB 15217 HNCO of #3 (15N 64 x 13C 80, naturally <= 85 per dimension) to NUS** -
   the sampling table is produced by NMRPipe's `uniform_to_nus`. **This page takes this option**: real
   Bruker-acquired data, small grid, at the cost that the **sampling table is generated by this project
   and is not an originally acquired NUS scheme**.

> **`scripts/vm_sample_make_nus.py` supports 2D only** (it derives the complex-point grid from
> `acqu2s TD / mult` and never reads `acqu3s`). The NUS sampling for #4 must therefore be produced on the
> real machine with NMRPipe's `uniform_to_nus` (section 5) - it **cannot** rely on that script.

## 2. Truth recovery: the result matches **deposited chemical shifts**

The figures in section 1 are a qualitative comparison; this section gives the numbers. Convention (same
source as `workflow/truth_benchmark.py`):

- **Matching**: `d = hypot(dH/tol_H, dN/tol_N) <= 1`, **one-to-one greedy nearest-first**; one detected
  peak can match only one expected peak, and an expected peak that was taken is recorded as "not
  detected"; only expected peaks inside the 1H/15N window actually covered by the spectrum enter the
  denominator.
- **Reference**: the deposited chemical shifts differ from the spectrum's own reference by a constant,
  calibrated **once** by a grid scan with progressively tightened tolerance and then **frozen** (the
  calibration only counts matches; it does not participate in window or parameter selection).
- **Chance background**: the expected peak table is **shifted independently per peak** by >= 5 matching
  radii (fixed seed, 200 rounds), and the same matching computes the fraction that would match "by
  accident" - recovery must always be read together with its background.
- **Both detection and refinement use the product's own convention**; candidates are not altered and
  peaks are not swapped to manufacture matches.

| | 1 2D uniform<br>BMRB 27493 | 2 2D NUS<br>SMILE ex. 2 | 3 3D uniform<br>BMRB 15217 HNCO | 4 3D NUS<br>#3 downsampled |
| --- | --- | --- | --- | --- |
| Experiment/sampling/dimension as judged by the software | pending real run | pending real run | pending real run | pending real run |
| Input fingerprint (files / bytes / sha256) | pending real run | pending real run | pending real run | pending real run |
| Origin of the expected peak table | BMRB first-party HSQC peak list (deposited shifts), `filter=backbone` | **not applicable** (no deposited peak list) | as #1, entry 15217 | **not applicable** (no deposited peak list) |
| Expected peak table (sha256; rows -> inside the spectrum window) | pending real run | - | pending real run | - |
| Final spectrum shape | pending real run | pending real run | pending real run | pending real run |
| Global reference shift (ppm, frozen after calibration) | pending real run | - | pending real run | - |
| Detected peak count | pending real run | pending real run | pending real run | pending real run |
| **Tight-tolerance recovery** (1H 0.01 / 15N 0.05 ppm) | pending real run | - | pending real run | - |
| Chance background under the same convention | pending real run | - | pending real run | - |

> The `-` in the #2 and #4 columns is not "not measured"; it means **the criterion does not apply to
> them**: the SMILE official examples have no deposited chemical shifts, so no external truth independent
> of this software exists. Inventing a peak table for them would mean manufacturing truth, so those two
> are presented only through the visual comparison of section 1 and the QC scores of section 3 - stating
> the boundary is more honest than manufacturing a number.

**Where the truth for #1 and #3 comes from (never hand-assembled)**: BMRB provides a **first-party** HSQC
peak-list endpoint for the entry (`api.bmrb.io/.../simulate_hsqc?format=csv&filter=backbone`), which is
itself computed from that entry's **deposited chemical shifts**. After fetching, convert it with
`scripts/bmrb_expected_to_csv.py` into the three-column format the truth script expects:

```bash
curl -o expected_27493_bmrb.csv \
  "https://api.bmrb.io/current/entry/27493/simulate_hsqc?format=csv&filter=backbone"
python scripts/bmrb_expected_to_csv.py --input expected_27493_bmrb.csv --entry 27493 \
    --output expected_27493.csv --report expected_27493.report.json
```

The converter only maps columns and records provenance (it writes the input sha256); it does **not**
decide "which peaks should appear in the spectrum" - whether a peak falls inside the window actually
covered by the spectrum is filtered by the truth benchmark itself from the spectrum's range (counting
out-of-window peaks in the denominator would be unfair). The expected peak table is not committed; only
its sha256 and peak count are filled into the table above.

The tolerance ladder is fixed at `(0.01, 0.05) / (0.02, 0.10) / (0.05, 0.50) ppm`: a loose tolerance
passes for everyone, so a tight tolerance is required to show that "peak positions really do line up".
The looser the tier, the higher the chance background under the same convention, so only the tight and
loose tiers serve as criteria; looser tiers are used only for classification.

**Detection-threshold convention (must be read together)**: the detection threshold is chosen by the user
for their sample; the software does not decide it for them. The product default of 35 sigma is intended
for strong-signal liquid spectra, and its value is that it "works in more situations" - it is **not** a
yardstick for judging a particular data set. The 12 sigma chosen by the reference workflow on this kind of
data applies only to the "expected peaks" set used during window selection
(`workflow/window_optimize.py`); it and the product's default detection threshold are two independent
constants and do not override each other.

The phase score looks at the positive/negative mass distribution of the whole spectrum, while recovery
looks at whether there is a peak at a given peak position; the two do not contradict each other. **When

convention has differed by ~20 points, so a bare number is not meaningful.

## 4. Automatic processing parameters

The product writes two scripts: the conversion `process/fid.com` (`bruk2pipe` plus `nusExpand`, which
expands the sampling table, then hands the data to NMRPipe) and the final-spectrum script
`process/d_001_process.com`. The tables below give the latter's processing chain per dimension, and
which step decides which parameter. **The recorded values are the 2026-09-22 2D uniform run**; the
parameters for the three newly added paths are recorded in the same form after their real-machine run.
Parameter provenance is the same for all four paths, because it is decided by the same optimisation
stages rather than per data set.

| Dimension | Processing chain |
| --- | --- |
| Direct (1H) | `SP -off 0.3 -end 0.98 -pow 1 -c 0.5` -> `ZF -size 4096` -> `FT` -> `PS -p0 300 -p1 0 -di` -> `POLY -ord 2 -auto` -> `EXT -x1 10.5ppm -xn 6.5ppm -sw -round 2` |
| Indirect (15N) | `TP` -> `SP -off 0.45 -end 0.95 -pow 1 -c 0.5` -> `ZF -size 512` -> `FT` -> `PS -p0 272.5 -p1 0 -di` -> `POLY -ord 3 -auto` -> `TP` -> `pipe2xyz -out d_001.ft2 -x` |

| Parameter | Final value (2026-09-22, 2D uniform) | Decided by |
| --- | --- | --- |
| Window function `SP -off/-end/-pow/-c` | direct 0.3 / 0.98, indirect 0.45 / 0.95 | **window selection**, scored on the reference spectrum (`workflow/window_optimize.py`) |
| Zero filling `ZF -size` | 4096 (1H) / 512 (15N) | zero-fill candidate rule (auto: from TD and memory) |
| Phase `PS -p0/-p1` | 1H 300 / 15N 272.5 (p1 = 0) | phase optimisation (direct dimension first, then a second search on the indirect one) |
| Baseline `POLY -ord N -auto` | direct 2, indirect 3 | baseline optimisation (`workflow/baseline_optimize.py`: per axis, scored over mode in {off, auto} x order in {1,2,3}; switched off it is a bare `POLY -auto`) |
| 1H display window `EXT` | 10.5 -> 6.5 ppm | the data's own 1H range (measured 1H 6.497-10.502 ppm in the final spectrum) |

**From before the optimisation (the reference script `process/d_001_before_optimize.com`) to the final run
only two things change**: (1) the direct-dimension window, `SP -off 0.45 -end 0.95` -> `SP -off 0.3 -end
0.98`; (2) both baselines, from a bare `POLY -auto` to `POLY -ord 2 -auto` / `POLY -ord 3 -auto`. The
indirect window, zero filling, phase and the 1H window are unchanged.

> For the NUS paths the chain additionally contains the SMILE reconstruction line in the indirect-dimension
> segment; the parameters of that line (iteration count, sigma, thread count) are constrained by the memory
> guard of section 0 and are recorded per data set after the run.

## 6. What this shows

- **The automatic spectrum agrees with the spectrum the data provider processed**, and for the two data
  sets with deposited shifts **the result matches an external ground truth**: after one global reference
  calibration, the expected peaks taken from the authors' deposited chemical shifts are matched one-to-one
  at the tight tolerance, while the chance background under the same convention is far lower - the
  criterion lives outside the software instead of comparing it with itself, and the input data are public
  BMRB timedomain entries you can download yourself.
- **The same input gives the same output**: the main-peak difference across three independent repeats is
  zero (section 5 for the 2D uniform path), and the spectra are accepted by QC (section 3).
- **What this comparison is for**: it demonstrates the **effectiveness of the processing program**, not a
  scientific conclusion. What you do with the processed results afterwards is your own business and has
  nothing to do with this software.
- **Scope, stated plainly**: the evidence on this page covers four specific public data sets on the stated
  dates. It does not establish performance on other data sets, experiment types, sampling schemes, or
  current source revisions. For #4 in particular, the sampling table is generated by this project rather
  than originally acquired, so its numbers speak to the NUS *processing path* and not to a particular
  acquisition.
