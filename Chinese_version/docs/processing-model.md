# 处理模型

本页说明 nmrForge 如何决定对一个数据集做什么、按什么顺序做,以及为什么这样分组。
它是 [architecture.md](architecture.md)(分层)与 [qc-system.md](qc-system.md)(质量指标)
的概念性同伴。

## 核心思路

「能跑通的脚本」不等于「本应采用的那个脚本」。因此 nmrForge 把处理拆成四组决定:

1. **理解** —— 这是哪种实验?它是怎么采样的?
2. **规划** —— 该走哪条处理路径、该用什么参数?
3. **执行** —— 用一份显式、可检查的脚本驱动 NMRPipe。
4. **说明** —— 记录质量指标、解析后的参数与告警。

第一步之后的每一步都是第一步的后果。如果实验或采样判定错了,后面的每一个选择都会错,
而质量指标并不能可靠地发现这种错 —— 所以判定被当作一道关卡,而不是一个提示。

## 第一步 —— 数据理解

| 决定 | 依据 | 位置 |
| --- | --- | --- |
| 维度数 | `PARMODE`,再看 `acqu2s`/`acqu3s` 是否存在 | `core/data/bruker_reader.py` |
| 维度角色与核 | 逐维度的 `NUC1`、`TD`、`SW_h`、`SFO1`、`O1` | `core/data/bruker_reader.py` |
| 每轴的采集模式 | `FnMODE`(`ft_kind_for`、`ft_alt_for`、`ft_neg_for`) | `core/experiment/acquisition_mode_detector.py` |
| 实验类型 | 脉冲程序、逐维度核组合、维度顺序、采集参数 | `core/experiment/experiment_classifier.py` + `presets/*.yaml` |
| 采样方式 | `nuslist`、脉冲程序、点数、实际数据长度、采集参数 | `core/experiment/sampling_detector.py` |

这里有两条规定:

- **文件名不是证据。**判定依据是脉冲程序与物理参数,不是目录名或文件名。
- **矛盾判为 `uncertain`,而不是猜一个。**如果元数据说是 NUS,而采样表其实覆盖了完整网格,
  nmrForge 会如实说明并拒绝处理,因为 uniform/NUS 判错会悄悄改变每个参数的含义。

`presets/*.yaml` 是实验模板的唯一数据源。模板声明期望的核组合、实验是相位敏感还是模谱,
以及诸如「是否适用自动相位搜索」这类处理提示。

## 第二步 —— 规划

规划是一张小依赖图(`core/planning/dependency_graph.py`),节点状态取
`PENDING`、`READY`、`RUNNING`、`DONE`、`FAILED`、`OUTDATED` 之一。节点以输入为键,所以:

- 一个昂贵的节点(比如 SMILE 重构)在它依赖的东西没变时不会重算;
- 一旦真有东西变了,下游全部标为 `OUTDATED`,而不是悄悄复用旧结果。

「昂贵重构与日常参数优化分开」这条原则就落在这里:NUS 重构是独立节点,
在便宜参数上的参数扫描不会强迫重新重构。

## 第三步 —— 执行顺序

顺序是固定的,而且不是随意定的:

```text
1  FID 层诊断                     (先于一切;任何修复都留日志)
2  基线优化                       (必须先于窗函数优化)
2.1 用选定的基线重新出谱
2.5 直接维窗函数优化
3  间接维窗函数优化
4  填零 / 最终尺寸
5  相位校正                       (自动搜索,或人工给的值)
6  最终运行                       (真正产出谱图的那份脚本)
```

这些约束为什么存在:

- **诊断最先。**坏点、非有限值与异常迹线会改变此后测到的每一个指标,
  所以在优化开始前就要找出来并报告。
- **基线先于窗函数。**窗函数打分用线宽、信噪比与线型;滚动的基线会扭曲这些分数,
  所以必须先去掉它。(这个顺序是吃过亏才定下来的,记录在 `docs/development.md`。)
- **窗函数先于相位搜索。**相位质量是在峰窗上打分的,而峰窗取决于所施加的窗函数。
  先定相位再优化窗函数,会让相位选择失效。
- **填零在倒数第二。**填零改变数字分辨率,因而改变「亚格点峰位」的含义;
  它必须在峰定位之前定下来,并且影响相位搜索的开销。

直接维与间接维都会真正做优化。窗函数候选池里包含「不加窗」,
因为一条自然衰减的轴理应以不加窗收场;采集上被截断的轴偏好温和的窗;
间接维打分时带一个显式的分辨率保持因子。

## 第四步 —— 记录什么

每次运行都写一份 `WorkflowRun` 记录(`core/project/models.py`),包含运行 id、输入引用、
解析后的参数、引用的脚本、产物、软件版本、外部工具版本(`core/version.py`)、时间戳与告警。
脚本与它产出的谱图都会保留,因此结果可以被重新推导,而不是只能被相信。

脚本化 API 会在研究目录下写一套对应的记录(`manifest.json`、`runs.json`)——
见 [external-api/06-outputs-and-records.md](external-api/06-outputs-and-records.md)。

## 参数解析

参数来自多个地方,它们按既定顺序合并,而不是靠运气。从优先级最低读到最高:

1. 实验模板默认值(`presets/*.yaml`);
2. `nmrforge_data/config/nmrforge.yaml`,以及用于机器本地覆盖的 `nmrforge_data/config/nmrforge.local.yaml`;
3. 参考运行的实际生效参数(用于参数扫描研究);
4. 批量层覆盖;
5. 逐组合覆盖(组合表里的空单元格表示「未指定」,不表示「设为空」)。

解析后的集合会逐运行记录,并记下每个值来自哪个来源。被请求但因故无法兑现的参数会以告警
报出,而不是被悄悄忽略 —— 例如为一条窗类型是 `none` 的轴写窗函数子参数是**错误**,
不是一个空操作。

## 维度与四条处理路径

nmrForge 把它们当作四条不同的路径,对处理行为的改动默认要适用于全部四条,
除非这个例外能被论证并写进文档:

| 路径 | 重构方式 |
| --- | --- |
| 2D uniform | 常规 FT |
| 2D NUS | SMILE |
| 3D uniform | 常规 FT |
| 3D NUS | SMILE |

确实允许的路径差异(例如 SMILE 要求在直接维用固定的切趾,或 3D 切片流式处理)
连同理由记录在 `docs/development.md`。

## 自动化的边界

nmrForge 自动化它能验证的东西,并如实报告它不能验证的东西:

- 模谱实验跳过自动相位搜索,因为它在那里没有意义;
- 窗函数候选按分辨率判据筛选,而不是永远取数值最高的那个;
- 在 SMILE 内部失败的重构就是一次失败的运行,绝不会变成「成功但谱不对」;
- 坏点**修复**是可选的、且一定留日志;坏点**检测**是无条件的。
