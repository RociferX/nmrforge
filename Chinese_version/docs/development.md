# 开发指南

本指南说明公开源码树当前的开发实践。运行时行为以实现为准。历史基准或发行说明只描述页面所记录的源码修订和输入，不代表当前代码树已经通过相同验证。

## 环境与依赖

Linux 是目标运行平台。Windows 可用于编辑源码，但 Windows 运行时行为不属于项目兼容目标。

如需安装可编辑的源码版本：

```bash
git clone https://github.com/RociferX/nmrforge.git
cd nmrforge
python -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
python main.py
```

可选依赖组和随包资源见[安装说明](installation.md)。项目配置和运行时资源分别位于 `pyproject.toml` 与 `nmrforge_data/`。机器本地配置放在 `nmrforge_data/config/nmrforge.local.yaml`；不要将开发者专用路径或凭据写入受版本控制的默认配置或示例。

NMRPipe 和 SMILE 是外部工具，不是 Python 包依赖，也不随源码树打包。数据转换和谱处理需要 NMRPipe；NUS 重构需要 SMILE。后端按配置的可执行文件/目录、`PATH`、已加载的 `csh` 环境和支持的常见位置查找 NMRPipe。精确优先级和能力边界见[外部依赖](external-dependencies.md)。缺少引擎时应明确报告能力不可用或给出可操作的错误，不得用替代结果冒充成功结果。

SMILE 的内存占用会随直接维大小和间接维重构网格显著变化。应用会在启动重构前估算所需预算。增加零填充或线程数前应考虑可用内存。真实引擎验收时应同时记录引擎版本。

源码发布和二进制发布是不同交付物。编辑或同步源码不会更新已有 AppImage。发布时必须标明二进制对应的源码修订；只有在确切的 AppImage 构建并检查后，才能称其为当前版本。

## 修改流程

保持改动聚焦，并说明行为变化、涉及路径及完成的验证。修改处理行为前，先查看相关公开契约和测试。考虑以下不同情况：

- 2D 与 3D 数据；
- 均匀采样数据和受支持的 NUS 布局；
- 自动与人工处理入口。

只有当某项操作本身只适用于特定路径时，才采用路径专用实现，并在面向用户的文档中说明适用范围和原因。

测试和夹具应能在另一套受支持的 Linux 环境中复现。无须真实外部引擎的场景，优先使用合成数据和伪后端。测试不得依赖开发者机器上的绝对路径、未随项目提供的私人数据集或固定的 CPU/内存假设。生成的测试数据、日志、缓存和临时文件应放在源码树之外。

## 测试与验证

迭代时先运行与改动最相关的检查，再在受支持的 Linux 环境中运行较完整的测试。测试类别见 [`tests/categories.py`](../../tests/categories.py)：

```bash
pytest -m unit
pytest -m integration
pytest -m regression
```

完整路径回归测试为：

```bash
python -m pytest tests/test_full_paths.py
```

该测试覆盖自动与人工的 2D/3D 均匀采样及 NUS 路径。当前批处理仅支持 2D；不要声称批处理覆盖了四种维度与采样方式组合。无可用显示器时，GUI 测试可设置 `QT_QPA_PLATFORM=offscreen` 运行。

不需要 NMRPipe 或 SMILE 的逻辑优先通过 mock/伪引擎检查。真实引擎验收须在安装相应工具的 Linux 环境中单独进行，并记录源码修订、输入说明、NMRPipe/SMILE 版本、相关参数、命令或工作流程及结果。mock 测试通过不代表真实引擎已执行，也不证明科学结论有效。

不要为了让当前文档看起来已验证而重跑或改写历史基准。应明确标注历史证据的适用范围；只有在另有计划时才开展新基准。

提交代码前运行相关测试和 `ruff check .`。处理路径变更在受支持的 Linux 测试环境可用时，还应包含完整路径回归。应如实记录环境限制，不能把跳过的真实引擎检查记作通过。

## 处理与数据契约

改动处理或记录逻辑时，须保留以下跨模块不变量：

- **采样：**使用标准 `nuslist`，或 `acqus.NUSLIST` 明确指定的文件。不能根据单独的整数列表或名义 NUS 百分比推断采样表。完整且为标准顺序的采样表可以走均匀采样路径；完整但顺序重排的采样表仍须按采样表定位。如果显式 NUS 元数据没有可恢复的采样表或采样位置，应拒绝导入，而不是猜测。尾部块填充不等于未采样点。
- **轴身份：**区分存储顺序、逻辑 F 轴身份和核身份。使用 `FDDIMORDER` 映射坐标轴；核相同不代表坐标轴可以互换。零 `ORIG` 是有效谱头值；值缺失时应保留为缺失，不要猜测替代值。
- **采集元数据：**保留 NMRPipe 对实/复点数和采集模式的语义，包括模式专用关键字及其 `-N` 变体。校验几何字段时不要强制使用历史 CAR 约定。谱宽冲突须显式解决，并在溯源信息中记录采用值及来源。
- **峰挑选：**不得无条件添加边缘屏蔽带。自动轴向筛选是保守启发式，必须同时具备兼容的实验/采集证据，以及原始数据边缘大量狭窄且对齐的候选峰。应保留内部峰、孤立边缘峰和有歧义的情况。用户指定的边缘宽度与自动筛选不同，必须单独记录。
- **峰定位：**当前支持的方法是三点抛物线定位。不要把已移除的高斯拟合控件重新作为当前选项公开。区分峰检测、峰表行数、每张谱内的峰编号，以及可选的定向定位。
- **背景与符号：**阈值、峰高、SNR 和参考测量遵循文档规定的全局中位数背景约定；该约定不修改谱图。自动符号处理遵循实验模板。相敏 COSY、NOESY 和 ROESY 保留正负两种符号；显式 API 符号请求优先。
- **对齐：**参考对齐是坐标操作，不得修改谱数据。匹配质量低或存在歧义时，不得静默删除候选峰。
- **分段频移：**`segment_shift_hz` 由用户指定，第一段使用 0 Hz。软件不会自动估算段间漂移，也不保证残差复检。只有实际应用了所请求的频移，才可记录为已应用；并应提示用户检查处理后的谱图。

输入、输出和错误的详细语义如有变化，应同时更新实现、[API 契约](API_CONTRACT.md)及相关[外部 API 参考](external-api/README.md)。

## Python 公共 API 与兼容性

公共入口文档统一使用以下五个英文小节标题：

```text
Parameters
Returns
Raises
Side effects
Examples
```

参数说明应包含类型和物理含义；示例必须使用当前支持的参数和输出。导出名称、API 参考页、CLI 文档和示例应保持同步。内部辅助函数不会自动成为公共 API。

`nmrforge_api` 兼容清单用于分类外部可观察到的变化。修改处理代码、公共输出或随包默认值时，应判断变化属于 `same`、`additive`、`behavior_changed` 还是 `contract_changed`。数值行为变化须注明影响范围；字段、列或错误码变化须同步更新公开契约。使用项目记录的兼容性工具和黄金向量流程；不要手工拼装运行标记或兼容记录。

完整 JSON 状态文档必须原子写入。仅追加日志和审计流属于不同记录类型。除非有意更新公开契约，否则应保留序列化形式和稳定标识符。

## 日志与面向用户的错误

库使用具名 logger，并且导入时不配置日志处理器；由应用入口配置日志。机器可读的 CLI JSON 输出到 stdout，诊断信息输出到 stderr。详细 traceback 应放在调试输出或运行日志中，不应直接显示在普通对话框里。

已知的输入和环境错误应说明用户下一步可采取的操作。未知错误应保留有用的异常细节，不要臆造原因，也不要只显示异常类名。操作失败不得静默转换为成功结果。

记录应区分请求值、已应用值、解析出的自动值、警告和失败。建议值不等于已执行的校正。QC 报告描述数据质量。
